# Screen-switch performance — Sep 2026

Probe: `qa/e2e/perf_probe.py` (iPhone 13 viewport in chromium, CPU throttled 4x, 80 ms round trip,
~12 Mbps). Budget tests: `qa/e2e/test_perf.py`. Times are ms from navigation start.

- **fcp**: first contentful paint · **chrome**: topbar + bottom nav mounted · **me**: `/api/auth/me` resolved
- **content**: first frame with no skeletons and ≥90% of the final text · **ready**: no skeleton, no fetch in flight
- **depth**: longest chain of API requests each waiting on the previous · **net**: shell files (HTML/CSS/JS/fonts) fetched over the network

Back: restored from the back/forward cache. The topbar and bottom nav are present at first paint on every screen
(chrome ≤ fcp). Revisited bottom tabs paint their kept copy, so their content time is the page's own render.

What changed, by phase: 1 service-worker shell cache stamped per deploy (0 shell files over the network, bfcache);
2 `/me` from the session cache and parallel boots (depth 1); 3 last-seen data on the bottom tabs, SVG sparklines,
memoised chart tokens; 4 crossfade between screens, no forced layouts during boot, pressed states, touch-action,
composited skeletons; 5 connection reuse, per-request settings memo, tenant-scoped counts, first-page-only
transaction totals, Server-Timing. Deploy drill: after an update the open app keeps the old build for the next
screen or two while the new worker installs, then serves the new build only (old cache deleted, no mixed files).
